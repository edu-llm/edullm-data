# Proposed changes to the pipeline as built (questioning the code, per owner instruction)

## P1 — STAGE-THEN-BUILD: copy sources to S3 once, then never touch HuggingFace again

**Today:** `_reader_for` streams live from HuggingFace inside the Batch container, and its own
docstring says this is **⚠️ UNVERIFIED against live HF from inside a Batch container** — every
offline test injects `documents=` instead.

**Proposed:** a Pass 0 that copies raw source files HF -> `s3://edullm-landing/_src/<source>/`.
No parsing, no tokenizing, no filtering. Then every later pass reads in-region.

| | cost |
|---|---|
| staging volume | ~6.1 TB compressed (parquet / jsonl.gz already compressed) |
| S3 Standard | **$140/month**, so **~$280** for a 2-month build window |
| HF -> AWS inbound transfer | **free** (AWS does not charge ingress) |
| per-pass read, staged | **0.17-1.35 h** (8 instances at 10 Gbit/s = 80 Gbit/s aggregate) |
| per-pass read, live HF | 2.71-5.42 h at 5-2.5 Gbit/s, and rate-limit exposed |

**Four things this buys beyond speed:**
1. **Extra passes become affordable** — which is what makes exact global dedup viable (P2).
2. **Resumability without HF** — a dead job re-reads S3, never re-hits HF rate limits.
3. **Reproducibility** — source bytes are pinned. An HF revision can move under us; a staged copy
   cannot.
4. **It retires the UNVERIFIED risk** in `_reader_for` — the highest-risk untested path in the
   build.

## P2 — GLOBAL dedup by hash-space partition, exact, no shared state

**Today:** per-bundle only (F4). DCLM alone = 862M docs = **74 GB** in one flat bundle.

**Rejected option — one global `set`:** 2.28B docs x 85.9 B = **195.9 GB**. Fits nothing.

**Rejected option — Bloom filter:** n=2.28B at fp=1e-6 is **8.20 GB, k=20 hashes**. Affordable,
but approximate: a false positive DISCARDS a real document, and 20 hashes per document is real CPU.
Keep as the fallback.

**Proposed — partition the hash space, 256 ways.** Each worker owns partition `p` and sees
documents from EVERY source whose `content_hash` falls in `p`. Cross-source duplicates land in the
same partition by construction, so the dedup is **exact** with **zero shared state**.

| partitions | hashes/worker | resident |
|---|---|---|
| 16 | 142.5 M | 12.24 GB |
| 64 | 35.6 M | 3.06 GB |
| **256** | **8.9 M** | **0.77 GB** |
| 1024 | 2.2 M | 0.19 GB |

**The constraint that shapes this:** the partition can decide dedup but **cannot** decide shard
placement, because shards must stay source-pure to carry a `source` label (F5). So it is a 2-pass
design: pass 1 emits `(hash, source, ref)` triples and resolves winners; pass 2 builds shards with
a dedup oracle. Triple volume = 2.28B x 26 B = **59.3 GB**, trivially sortable in S3.
2-pass is only affordable **because of P1**.

## P3 — Gate A: pool + thread, and stop treating shard size as the lever

**Today:** 6 serial round trips per object, on a **10-connection** default pool (F2, F3).
MEASURED 507.5 ms/object => 40,000 objects = **5.64 h** against a **2.0 h** cap.

**Proposed, in order of leverage:**
1. **Raise `max_pool_connections`** on the client `s3.py:196` builds. It passes no `Config` at all,
   so it inherits 10. Threading against a 10-connection pool self-throttles.
2. **Thread the profile checks.** `validate.py:577` already threads the size sweep with
   `head_workers`; `profiles/pretrain_tokens_v1.py` has **zero** threading. Same pattern, ~20 lines.
   At 16 workers, 40,000 objects = **21 min**.
3. **Batch the 4 decode windows into 1 ranged GET** where the offsets are close enough, or accept 4.
   `_N_WINDOWS = 4` plus a HEAD plus an npy sniff is 6 round trips; the HEAD is avoidable when the
   manifest's declared `bytes` is already being compared (read the size from the ranged GET's
   `Content-Range` instead).

**Consequence: shard size stops being forced by the validator.** Then pick it on mixture error and
OLMo-core's read pattern instead, which is the right basis.

## P4 — extend boundary-marker neutralization before ingesting any chat-derived source
Covers exactly ONE literal today, behind a `"<|"` prefix guard (F10). The new mix adds
Nemotron SFT, dolma3-midtrain, reasoning traces and Cosmopedia — all generated by chat models.
Add `<|im_start|>`, `<|im_end|>`, `<|eot_id|>`, `<|end_of_text|>`, `</s>`, `<s>`, `[EOS]`,
`<end_of_turn>`, and replace the single-prefix guard with a multi-prefix test.

## P5 — the two-stage corpus needs a topology decision, and the label schema forbids the obvious one
`PATH_LABEL_KEYS = ("source", "domain")` is exactly 2 deep and `labels_from_path` RAISES deeper
(F6). So "stage" cannot be a third path segment. Options:
- **(a) fuse stage into `source`** (`dclm-s1`, `dclm-s2`) — works today, doubles the source
  vocabulary, and makes a single-source mixture predicate awkward.
- **(b) two datasets** — clean, but `build_mixture` is single-dataset by construction, so no
  mixture can ever span both. Fine IF the trainer stages sequentially, which is what a cooldown IS.
- **(c) one dataset, trainer stages it** — publish once, let the training config draw different
  ratios per phase.
**(b) is the recommendation**: a cooldown is sequential by definition, so nothing needs one mixture
spanning both stages, and it keeps the 5-digit ordinal space (F7) from being consumed twice.
